## Summary

Add `prepend` as a class/module/struct body keyword, analogous to `include` and `extend`, that inserts a module _ahead_ of the enclosing type in its method-resolution order. Methods defined in a prepended module override the type's own methods of the same name and can delegate to them with `super`.

```crystal
class Base
  def foo; puts "Base"; end
end

module Tracer
  def foo
    puts "Tracer"
    super
  end
end

class Service < Base
  prepend Tracer
  def foo; puts "Service"; super; end
end

Service.new.foo
# Tracer
# Service
# Base
```

## Motivation

Crystal today has no first-class way to _wrap_ an existing method without rewriting its definition. `include` adds a module behind the including type in the lookup chain, so any method the host already defines wins outright — the included module's same-named method is unreachable through ordinary dispatch.

To put logging, instrumentation, retries, transactions, or any other cross-cutting wrapper around an existing method, users today have to:

- **Open the class and use `previous_def`.** Works, but each callsite is hand-coded into the host, the wrapper can't be a reusable module, and combining several wrappers becomes a sequence of monkey-patches whose order is whatever the requires happened to be.
- **Build a proxy / delegator.** Object identity changes, downstream code that expects the underlying type breaks, and method forwarding has to be written by hand or generated by macro.
- **Macro-rewrite the method.** Effective but invasive; every wrapper has to learn macro authoring, and the original method's source location is lost from stack traces and tooling.

None of these compose: stacking two independent wrappers is hard to do cleanly even when each one in isolation works.

`prepend` directly addresses this. A wrapper module defines its method, calls `super`, and is enabled on a host by adding one line — `prepend Tracer` — to the host's body. Multiple wrappers compose naturally: each lives in its own module, the order in which they're prepended is the order in which they wrap, and removing one is removing one line. The pattern is well-trodden in other languages (Ruby's `prepend`, Python's decorators, "around" advice in AOP) and reduces a class of monkey-patching workarounds in Crystal to ordinary declarative code.

The implementation is small and orthogonal to existing features — it's a new lookup root, not a change to existing lookup — so the cost-to-value is favourable. The change also closes a long-standing parity gap with Ruby, easing porting of Ruby code that uses `Module#prepend`.

## Guide-level explanation

`prepend Mod` is the third way (after `include` and `extend`) to mix a module into a class, struct, or other module. Unlike `include`, which adds the module _after_ the host in the method lookup chain, `prepend` adds it _before_ the host. The result is that the prepended module's methods are found first, and the host's methods become reachable through `super`.

```crystal
class Base
  def foo; "Base"; end
end

module Wrapper
  def foo
    "Wrapper(#{super})"
  end
end

class Service < Base
  prepend Wrapper
end

Service.new.foo
# => "Wrapper(Base)"
```

`prepend Wrapper` placed `Wrapper` ahead of `Service` in the lookup chain. `Service.new.foo` finds `Wrapper#foo` first; `super` inside `Wrapper#foo` delegates to the next definition, which is the inherited `Base#foo`.

### Interaction with the host's own methods

`prepend` is most useful when the host has its own definition of the wrapped method:

```crystal
class Service
  prepend Wrapper
  def foo; "Service"; end
end

module Wrapper
  def foo; "Wrapper(#{super})"; end
end

Service.new.foo
# => "Wrapper(Service)"
```

The lookup order here is: `Wrapper` → `Service` → ancestors. `Wrapper#foo` is found first; its `super` resolves to `Service#foo`.

### Interaction with `include`

`include` and `prepend` are independent. A class can do both. The full method-resolution order is:

```
prepended modules (in the order they appear, most recent first)
self
included modules / parent classes (regular ancestors, as today)
```

```crystal
module Front; def foo; "Front(#{super})"; end; end
module Back;  def foo; "Back";              end; end

class Service
  prepend Front
  include Back
end

Service.new.foo
# => "Front(Back)"
```

If `prepend Front` is replaced with `include Front`, both `Front#foo` and `Back#foo` appear among the regular ancestors and the usual include-order rules apply (and `Service#foo`, if defined, would win regardless). `prepend` is what makes the wrapping visible at the call site without the host having to know.

### Composing multiple `prepend`s

Several modules can be prepended. Each `prepend` puts its argument at the head of the chain, so the _most recently_ prepended module is found first. Each wrapper's `super` goes to the next one down the prepended chain, and the last one's `super` reaches the host:

```crystal
module Timer;  def foo; t = Time.utc; r = super; puts "#{Time.utc - t}"; r; end; end
module Trace;  def foo; puts "→ foo"; r = super; puts "← foo"; r; end; end

class Service
  prepend Timer    # outermost
  prepend Trace    # innermost (closer to the host)
  def foo; do_work; end
end
```

`Service.new.foo` runs `Timer#foo`, which calls `super`, which runs `Trace#foo`, which calls `super`, which runs `Service#foo`.

### The `prepended` hook

A module can react to being prepended just like it can react to `include` / `extend`:

```crystal
module Auditable
  macro prepended
    @@audit_log = [] of String
  end

  def perform
    @@audit_log << "#{Time.utc}: perform"
    super
  end
end
```

`macro prepended` fires once per host, on the host, exactly like `macro included` and `macro extended`. This means the wrapper module can establish per-host state (class vars, hook annotations, generated helpers) at the moment it's wired in.

### Errors

Cyclic prepending is rejected at compile time:

```crystal
module A; prepend B; end
module B; prepend A; end   # error: cyclic prepend detected
```

Prepending a non-module (e.g. a class) is rejected — `prepend` mirrors `include` in that respect:

```crystal
class Foo; end
class Bar
  prepend Foo            # error: Foo is not a module
end
```

Prepending `self` is rejected.

### How to think about it

`include` says "these methods are available on the host, but the host's own definitions win." `prepend` says "these methods _replace_ the host's own definitions, and the host's are still reachable via `super`." The first is composition; the second is wrapping. The two are deliberately separate so the reader of a class body can tell at a glance which is in play.

## Reference-level explanation

### Syntax

`prepend` is recognised as a body-level statement everywhere `include` and `extend` are: directly inside a `class`, `struct`, or `module` body, and at the same nesting depth. The grammar parallels `include`:

```
prepend_stmt ::= "prepend" type_expr
```

`prepend` is reserved as a keyword in body-level statement position. As a method call on a value (`array.prepend(x)`) it remains usable, because that's not statement position.

### Semantics

#### Lookup chain

Each `ModuleType` (class, struct, generic-instance, non-generic module, generic module) gains a `prepended_modules` list in addition to its existing `parents` list. `prepend Mod` inside a body inserts `Mod` at the _head_ of `prepended_modules`. The most recently prepended module is therefore at index 0.

Method resolution for `receiver.foo` on a value whose static type is `T` walks:

1. `T.prepended_modules`, in order (head-first).
2. `T`'s own methods.
3. `T.parents`, as today (included modules, superclass, etc.).

This is the only change to the lookup algorithm. Steps 2 and 3 are unmodified from current behaviour.

#### `super`

`super` inside a method `M#foo` resolves to "the next definition of `foo` after `M` in the resolution chain of the call's receiver." With `prepend`, the chain for a receiver of type `T` is:

```
T.prepended_modules[0], T.prepended_modules[1], …, T, T.parents…
```

So:

- `super` inside a method on `T.prepended_modules[i]` resolves first to `prepended_modules[i+1]` if one exists with a matching definition, then to `T`'s own method, then to `T.parents`.
- `super` inside a method on `T` itself resolves only to `T.parents`. It does _not_ re-enter `prepended_modules` — the host's own `super` continues to mean "delegate to the inherited definition," exactly as it does today.

This asymmetry is the same one Ruby has: prepended methods are aware they are wrapping (their `super` walks the chain including the host); the host is not aware it is being wrapped (its `super` does not see the wrappers above it).

#### Ancestors

`Type#ancestors` retains its current meaning: it returns the regular ancestor chain only, not the prepended modules. This preserves the trivial implementation of `super`-from-host described above.

A new accessor, `Type#ancestors_with_prepended` (or similarly-named), returns the full MRO with prepended modules at the head. This is the form exposed to macros, so `TypeNode#ancestors` in macros returns the full chain (matching Ruby's `Module#ancestors`).

#### Hooks

`macro prepended` is added alongside the existing `included` and `extended` hooks. It fires once per host, on the host, with `@type` bound to the host. The standard `Hook` plumbing is extended with a `Prepended` kind.

#### Errors

- **Cyclic prepend.** When `prepend Mod` is processed, both `Mod`'s regular ancestors and its prepended ancestors are walked. If the enclosing type appears anywhere in that chain, the compiler rejects the declaration with a "cyclic prepend" error.
- **Non-module argument.** `prepend` requires its argument to resolve to a module type. Classes, structs, primitive types, etc. produce a clear error pointing at the `prepend` line.
- **Self.** `prepend self` is rejected outright.
- **Duplicate prepend.** Prepending the same module twice has no effect (the module is already at the head; the second call is a no-op).

### Worked example

```crystal
class Base
  def foo; "Base"; end
end

module Included
  def foo; "Included(#{super})"; end
end

module Prepended
  def foo; "Prepended(#{super})"; end
end

class Service < Base
  prepend Prepended
  include Included
  def foo; "Service(#{super})"; end
end

Service.new.foo
# => "Prepended(Service(Included(Base)))"
```

Resolution order for `Service` instances:

```
Prepended → Service → Included → Base
```

- `Service.new.foo` enters `Prepended#foo`. Its `super` continues the chain at `Service`.
- `Service#foo`'s `super` does _not_ re-enter prepended modules; it walks regular ancestors, reaching `Included#foo`.
- `Included#foo`'s `super` continues to `Base#foo`.
- `Base#foo` has no `super`.

The final string composes outward: `Prepended(Service(Included(Base)))`.

### `prepend` and generic modules

`prepend GenericMod(T)` follows the same rules as `include GenericMod(T)`: the parameter types must be resolved at the point of the `prepend`, and the module instance is what ends up in `prepended_modules`. Free variables in the argument are resolved through the enclosing context.

Prepending into a generic _module_ (rather than into a class/struct) is allowed — the prepended module sits ahead of the generic module in the lookup chain of every type that includes the generic module.

### Visitor / AST

A new `Crystal::Prepend < ASTNode` node mirrors `Include`. The standard visitor, transformer, formatter, `to_s`, and codegen plumbing receive `prepend` overloads alongside the existing `include`/`extend` ones. No existing node's semantics change.

## Drawbacks

- **A second mechanism that looks similar to `include`.** A reader who hasn't met `prepend` may assume it's a synonym for `include`. The visible difference at the call site (whose method runs) is only apparent once a `super` is in play. Documentation and error messages must make the distinction concrete.

- **Encourages action-at-a-distance.** A prepended module changes the meaning of a method on the host without the host's definition mentioning it. That is the whole point of the feature, but it also means a reader of `Service` may be surprised when a method does something other than what `Service` defines. The cost is mitigated by the requirement that `prepend Mod` appears literally in the host's body (or in a `prepended` hook of something the host includes) — so the host is always one source-grep away.

- **Keyword reservation.** `prepend` becomes a body-level keyword. Code that defined `def prepend` at the top level (rather than as a method on a type) would break. Mitigated by the fact that `array.prepend(x)` and similar method-call use sites continue to work — only statement-position use is reserved.

- **MRO subtlety with `super`.** The `super`-from-host versus `super`-from-prepended distinction is correct but non-obvious. Documentation should call this out explicitly, and at least one canonical example should appear in the language reference.

- **Compile-time cycle detection cost.** Each `prepend` walks the candidate module's ancestor chains (regular and prepended) to detect cycles. This is `O(n)` in the size of those chains per `prepend` statement; negligible in practice, but a new linear-in-types check that didn't exist before.

## Rationale and alternatives

- **Status quo (`previous_def`).** `previous_def` works for wrapping a method _from within the same class_, but it can't be packaged as a reusable wrapper — every callsite has to be hand-edited. `prepend` is what makes the wrapper a first-class artefact.

- **Status quo (proxies / delegates).** A proxy changes `is_a?`, breaks code that relied on the underlying type, and forces every method to be forwarded by hand or by macro. `prepend` keeps object identity and adds zero forwarding cost.

- **Macro-rewrite of methods.** A macro can rewrite a method body to add a wrapper. This is functional but high-friction: every wrapper needs its own macro, source locations and tooling get confused, and combining wrappers becomes an authoring problem rather than a declarative one.

- **A separate "around" decorator syntax.** Some languages introduce dedicated wrapper syntax (`@around`, `@advice`, etc.). That works but requires inventing a new sub-language. `prepend` reuses the module + `super` vocabulary the user already knows.

- **Inheriting from a wrapper class.** Wrappers as classes only work when the type can inherit from them, which forecloses on inheriting from anything else. Modules are unconstrained that way.

The proposed design is the smallest change that closes the gap: one new keyword, one new list per type, one targeted change to `super`. It composes with everything Crystal already has rather than introducing a new dispatch mechanism alongside the existing one.

The impact of _not_ doing this is that the cross-cutting-concern patterns — logging, instrumentation, retries, transactions, telemetry — will continue to be reinvented through monkey-patching, macros, or proxies, in shard after shard, without a shared idiom.

## Prior art

- **Ruby.** `Module#prepend` was added in Ruby 2.0 and is the direct inspiration for this proposal. The semantics described above match Ruby's: prepended modules appear before the host in `Module#ancestors`, prepended methods can call `super`, the host's `super` does not re-enter the chain, and a `prepended` hook is fired. Ruby's experience after a decade of `prepend` in the wild is that the feature is most heavily used by instrumentation and library-integration tools (Rails autoloading, AppSignal, Datadog, etc.), and that the wrapping semantics are stable and well-understood.

- **Python.** Decorators (`@decorator def f(): ...`) provide method-level wrapping with a similar shape. `prepend` is the module-level analogue: rather than wrapping one method definition at a time, a module bundles a set of wrappers that get installed in one declaration.

- **AspectJ / AOP.** "Around advice" is the AOP term for the pattern. AspectJ users will recognise prepended modules as the lightweight, in-language version of an around aspect, without a separate weaving step.

- **Crystal `include`/`extend`.** The mechanics — body-level keyword, ancestor chain entry, lookup propagation, macro hook — are directly parallel. The implementation reuses the same machinery wherever possible, which limits the surface area of the change.

## Unresolved questions

- **Post-definition `prepend`.** Ruby allows `SomeClass.prepend(Mod)` to be called after the class has been defined. Crystal classes are reopenable, but the type structure is finalised at class body level. Whether and how to support post-definition `prepend` is left to a follow-up RFC.

- **Prepend into a generic module instance.** The cyclic check handles it, but the lookup paths haven't been heavily exercised. The behaviour is intended to be a direct extension of "prepend into the generic module" but the spec coverage to confirm that has not yet been written.

- **Keyword reservation scope.** `prepend` is reserved as a body-level keyword. Should it be reserved _only_ in class/module/struct body context, leaving `def prepend` at the top level legal? The conservative choice (reserved everywhere, parallel to `include`) is what's proposed; a narrower reservation is an alternative.

- **`Module#ancestors` macro shape.** `TypeNode#ancestors` returning the full MRO with prepended modules at the head matches Ruby. A separate `TypeNode#prepended` would expose only the prepended chain. The latter is mechanical to add once the former is in.

## Future possibilities

- **`Module#prepend` at runtime / post-definition.** As mentioned in unresolved questions.

- **Interaction with `final` modifiers.** If/when Crystal grows `final` for methods, the interaction with `prepend` (can a final method be wrapped?) will need to be specified.

- **Prepend ordering controls.** Right now the most recent `prepend` wins; explicit ordering primitives could be added later if real-world use surfaces the need.

- **Static analysis tooling.** A documentation lint that warns when a method on a frequently-prepended class is silently overridden by a prepended module would help readability; the data needed for it is already in the type model after this RFC lands.
